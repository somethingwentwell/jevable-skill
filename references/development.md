# Developing the standalone core

## Permanent independence boundary

This core builds and runs without Jarness, the desktop app or their checkout. No imports, process launch/discovery/attachment, shared state or credentials, synchronization, checkout links/mounts or fallback to those systems are permitted. Copied and independently maintained code may retain its required license attribution; attribution is not a dependency. Future desktop/Jarness adapters call the core SDK/API, never the reverse. Local SDK/CLI execution requires neither Docker nor a persistent authoring server. Optional Docker/Kubernetes workloads execute the **Jevable workflow runtime**, not the skill or authoring agent.

Run `npm run test:boundary` for adversarial path/link guards. After building and installing the actual tarball in a fresh directory outside the checkout, run `npm run test:standalone -- --installed /absolute/path/to/node_modules/@jevable/core`. This checks package/lock dependencies, shipped bytes, canonical bundle inputs and installation links, then executes installed CLI/reopen, SDK and a freshly exported Node-only workflow app with an empty PATH and private independent state. It needs no Jarness or Docker service. The build also enforces canonical core ownership for all three bundled runtime programs. This is a permanent release gate; passing it does not qualify browser behavior, providers, production observability or a live cluster.

Experimental `LocalRuntime` and `PostgresRuntime` `startWithGrant`/`readWithGrant` admit pinned retained-release starts and isolate own-run completed results, with immutable private creation binding and transaction-time authorization rechecks. `cancelWithGrant` adds own-run cancellation with derived private attribution and receipt-only retries that never repeat abort or settlement. `decideWithGrant` pins exact reviewer run/attempt/revision/actions and safely observes identical requests without continuation. PostgreSQL delegated mutations require the matching grant/run admission pins, time/deadline and journal batch request UUID; replay checks the retained batch link. See [grant integration](grants.md), including separate opt-in management caller start/read/checkpoint/control/cancel and reviewer HTTP/CLI paths. SDK use is server-free; transport requires an explicit independent host/instance, never Jarness or desktop discovery. Guarded caller controls require the creating grant's explicit control permission, an opaque checkpoint and a retained request identity; control permission does not grant read or approval authority. Actual storage/model/observability and deployment qualification must be recorded separately for each profile. New runtime bytes require renewed package/SQL/image evidence; prior checkpoints remain historical.

Human Approval is supported inside bounded For Each/Repeat Until bodies through the shared evaluator and SQLite/PostgreSQL hosts. Waiting/cancelled checkpoints, decision/request journal correlations, inbox/evidence/notification metadata and preview protocol retain optional loop scope; unscoped serialization is unchanged. See [review each loop item](authoring.md#review-each-loop-item) for deadline/control semantics. No database migration or automatic timer/decision is introduced. Current-byte package, SQL and deployment qualification are recorded separately; older bundle receipts do not qualify the new runtime bytes.

Configured reviewer telemetry joins an actual approval segment to the same guarded `approval-decided` commit. Shared historical checks require the segment/event chain to match for delegated runs; transition validation only admits this atomic append on a bound reviewer decision, never an owner decision or unrelated event. Paused/rejected cases end the span after settlement, continuation reuses it, and errors end as failed-or-uncertain. Receipts/reopen never reconstruct observations. Keep SQL, received-signal/model, installed/extracted programs and deployed profiles distinct when qualifying this behavior. Do not assume older writer binaries understand the atomic decision-event segment field; retain exact binary pins and an explicit upgrade/recovery plan.

Use [command-scoped discovery](cli-help.md), such as `help projects run --json`, for this installed version's actual positional count and parser flags. Help never opens state or services; `runtime start` exposes separate local/Docker grammars. The curated command index is tested against the dispatcher, while flags/counts are captured from that dispatcher's real parse call. This does not replace the remaining complete authoring/operator walkthrough audit.

The build also produces a dependency-bundled management CLI with both release-runtime assets. `runtime export --output management.zip` packages it for execution without npm, an installed skill or a source checkout; see [management distribution](management.md). The isolated-package qualifier exercises the extracted CLI and management API separately from the ordinary npm installation. [Docker ownership](docker-owner.md) adds the explicit host CLI/SDK lifecycle for a SQLite management container, including selected-owner import/release routing with host-side packaging. The experimental Docker-backed HTML gateway shares the local preview protocol without local workflow storage; see [live preview](live-preview.md). Browser and broader deployment qualification remain unfinished.

`@jevable/core/deployment` and `releases export-kubernetes` generate offline exact-release PostgreSQL deployment bundles. See [Kubernetes export](kubernetes.md) for reviewed image/option inputs, private Secret staging, readiness and explicit network policy. This adds no registry/cluster client dependency and does not qualify cluster execution. Installed-package checks use a clearly synthetic image receipt to test the export contract, not deployment behavior.

This repository is the future Jevable implementation owner. The skill and CLI consume its libraries; future desktop/harness adapters should consume this core, not the reverse. Source extraction receipts and original license notices are in `notices/`. Extraction included the source working tree's existing changes and did not modify it.

Prerequisite: Node.js 22.19 or newer and npm. The initial tested host is macOS arm64; cross-platform runtime qualification is pending. No Docker is needed for offline commands.

**Public-checkout test coverage.** Every test file loads and runs in a public clone; none is skipped or excluded. Five test-support scripts were missing from the public repository, and no originals were available, so they are **reconstructions** written from the tests' expectations. Each file's header says so:

- `scripts/tls-fixture.mjs` (+ `tls-fixture.d.mts`): one self-signed P-256 certificate per call that is also its own trust anchor, plus a free-port helper. It needs the OpenSSL CLI with `req -addext`.
- `scripts/check-telemetry-package.mjs` and `scripts/check-postgres-telemetry.mjs`: minimal independent OTLP protobuf decoders (`fields`, `metricSums`, `logRecords`, `resourceAttributes`, `traceRecords`).
- `scripts/check-documentation-package.mjs`: local-link checks for an installed package's Markdown and HTML contact sheets; also runnable as `node scripts/check-documentation-package.mjs <package-root>`.
- `scripts/release-guide-contract.mjs`: parsers for an exported app's `README.txt` telemetry examples and command reference.

They may differ from the private originals. In particular, the originals were probably also standalone package/PostgreSQL check runners; only the functions the tests import are rebuilt. One guard still fails in a public clone: `postgres-caller.spec.ts` › *preserves every previous caller/reviewer domain case and assertion* compares the file with a private qualification snapshot (`qualification/runner-snapshots/…`). That snapshot is not public and is not fabricated, so the test fails with an explicit "Missing private qualification snapshot" error instead of being skipped. `tests/provider-trace-fixture.d.ts` (part of the original repository) types the telemetry helpers. The `npm run test:boundary`, `test:standalone` and `test:package` scripts named above are not defined in the public `package.json`.

The package qualification packs this repository, installs the resulting tarball in a fresh temporary directory with production dependencies, and invokes the shipped binary and SDK. It checks that shipped JavaScript has no Jarness/harness/deepseek imports, workspace dependencies or source-tree references. Attribution text is not a dependency. It leaves its isolated directory available for inspection. The HTTPS integration/package checks require an OpenSSL CLI supporting `req -addext` to generate temporary test-only certificates; OpenSSL CLI is not a runtime prerequisite. Fixture private keys stay in temporary directories, not shipped artifacts. Actual image/platform records are pinned to their own runtime hashes and are not refreshed merely because local package tests pass.

The npm distribution also includes [Archify documentation diagrams](../architecture/README.md), editable JSON, screenshot contact sheets and the retained MIT notice. `scripts/check-documentation-package.mjs` checks local links across the installed README, skill instructions and reference guides, plus diagram/contact-sheet assets, and refuses missing or checkout-linked files. Private developer receipts and roadmap files stay in the source checkout; references to `qualification/*.json` in these guides identify those source-checkout records, not installed downloads. File integrity does not qualify browser rendering or workflow testing, and the diagrams' optional remote font stylesheets are not fetched by this check.

`src/workflow` owns compiler/import semantics, `src/templates` owns UI-independent builders, `src/runtime` owns the reused evaluator and standalone SQLite host, `src/projects` owns the replay-validated authoring journal, `src/preview` owns the experimental portable renderer and project-scoped live controller, and `src/providers` owns configuration, credentials, request evidence and the explicit OpenAI-compatible/System One transports. `src/cli.ts` is a command adapter; `src/http` is the explicit single-owner HTTP/HTTPS service/client adapter ([HTTP guide](http.md)), with opt-in [live preview](live-preview.md) or exact-release execution. `src/releases` owns immutable releases and the bundled execution entrypoint; `src/telemetry` owns opt-in trace/metric/log export; `src/images` owns explicit local image build/save ([image guide](images.md)). No module import starts a server. Proxy/multi-user authorization and deployment, browser preview qualification, richer live testing/debugging, real native-provider and deployment qualification, public-network/proxy ingress, managed Docker authoring and full observability remain pending; see `todo.md`. Do not claim all-platform, browser or deployment qualification from local protocol/controller-double tests.

## Runtime SDK and persistence

[Explicit API entry](api-trigger.md) adds an optional immutable start/test/generation mode shared by both hosts. Default manual/chat serialization remains unchanged. Release graph admission is separate from execution-mode admission; unsupported webhook/Custom families remain refused. `scripts/check-api-trigger-package.mjs` exercises installed SDK/CLI, authenticated loopback management/exact-release APIs, generated suites and fresh Node-only release apps; it is not a browser/container/production ingress qualifier.

The read-only [`@jevable/core/evidence` SDK and `runs export-bundle`](evidence-packages.md) package exact run/revision selections with historical test assessments. They compose the current owner's evidence/test reads; no storage schema, execution path or restoration behavior changes. `scripts/check-evidence-package.mjs` exercises the installed CLI across explicit local/PostgreSQL/Docker owners and compares the public local SDK's bytes. `runs inspect-bundle` and `inspectEvidenceZip` inspect archives offline through a shared bounded ZIP reader, without opening runtime state or displaying payloads. Project import reuses the same reader and pins its hash to an owned byte copy. `scripts/check-evidence-inspection-package.mjs` compares installed and extracted-management reports. Shared project/release ZIP packagers can attach an explicitly reviewed archive without restoring it. Experimental preview evidence, runnable-release and editable-project controls use those same packagers; `scripts/check-preview-evidence-bundle.mjs`, `scripts/check-preview-release.mjs` and `scripts/check-preview-project.mjs` exercise actual scoped protocols and installed artifact consumers. Those checks and serialized controller doubles do not qualify real browser saving or deployment.

For read-only observation of a service-owned run, use [`runs watch` or the `watchRun` SDK generator](watch.md). Neither opens storage or replays execution; terminal/attention states, deadline and interruption have distinct outcomes. This is sampled metadata, not a complete event stream.

For read-only installation, private configuration and explicit service compatibility checks, use [doctor](doctor.md). It shares PostgreSQL startup admission without opening a database, and checks shipped runtime bytes without executing them. It does not acquire an owner, initialize/migrate storage or automatically repair a crash lock.

`src/runtime/run-ledger.ts` owns the database-independent checkpoint replay used by both SQLite and PostgreSQL run stores. Its caller resolves checked historical project/release/test snapshots and journal events; the ledger performs no storage access, model dispatch or telemetry export. It verifies source/checkpoint, prepared attempts, cancellation/control evidence, trace linkage and exact creation provenance. Settled model evidence is verified separately. This does not prove every historical transition or external outcome. Valid existing SQLite records require no migration; inconsistent creation evidence is refused as corrupt rather than repaired automatically.

The experimental [`@jevable/core/storage` PostgreSQL SDK](postgres.md) exports `PostgresRuntime` for direct-source and reviewed project/release/test execution, approval/control/cancellation and configured model evidence under one database owner. It shares the awaited driver in `src/runtime/execution.ts` with `LocalRuntime`; both hosts preserve review guards across async boundaries. The PostgreSQL host exposes owned authoring/transfer/schema-generation adapters and assesses retained test runs against their historical accepted expectations. New run creation rechecks current project/test review after model admission. Guarded archived deletion checks retained runs, releases, all historical test definitions and even empty generation batches under the same typed-mutation queue, then commits a tombstone, immutable receipt and audit events atomically. It never cascades. The PostgreSQL SDK now supports opt-in OTLP execution traces/metrics/logs with durable linked contexts, owned async credentials, guarded provider mutation and idle export shutdown. Read-only v2 evidence exports preserve exact PostgreSQL sequence IDs and coherent checkpoint/journal observations. Default service startup/direct jobs use SQLite; release apps pin SQLite or PostgreSQL independently at creation; jobs explicitly select PostgreSQL with `--storage postgres --database-file <private-file>`. The separate `@jevable/core/http/postgres` SDK entrypoint starts a PostgreSQL management service with actual database health, paginated operations, explicit direct HTTPS and owned request drain before telemetry/storage shutdown. The CLI can start that service with `runtime serve --storage postgres --database-file <private-file>` and operate it through `runtime status/request`; direct SDK-backed CLI jobs are also available without HTTP. Explicit reviewed-snapshot release serving is also available through SDK/CLI with release-scoped operations and cursors. PostgreSQL app ZIPs and explicit image build inputs are implemented with separate backend bundles; scoped PostgreSQL loopback preview is implemented separately, while real-browser verification, production database deployment and full cluster observability remain open. PostgreSQL container execution, verified database TLS and host-loopback HTTPS are scoped to the separate [image profile](images.md#run-independently-with-postgresql), not inherited from SQLite. Read the guide before using the SDK or opt-in database qualification. Do not substitute the old harness's storage services for missing domain integration.

SDK change in this unpublished alpha: `LocalRuntime.check(yaml)` now returns a promise; use `await runtime.check(yaml)`. `ModelCalls.admit` may be asynchronous, and all runtime admission paths await it before dispatch. The shared configured-model adapter awaits storage reads, intent commits and settlement commits. Pending admissions reserve their run ID, block owner close/config changes, recheck reviewed project/test generations and preserve concurrent cancellation. CLI/API JSON results remain resolved objects, not serialized promises.

The experimental live graph uses the pure `projectPreviewExecution` SDK export to map exact-revision receipts into metadata-only node/connection evidence. Scoped loop iterations, selected ports, timing, usage and trace IDs remain distinct from raw source/input/output and actors. New port choices are retained with their settlement journal and disambiguate same-target routes; legacy records remain adjacency-only. Selected routes do not prove target completion or successful loop-return binding. Serialized viewer/controller doubles and real local receipt tests cover data/state behavior, not browser rendering. See [live-preview evidence semantics](live-preview.md#recorded-execution-graph).

SQLite schema 14 adds cooperative Pause control admission to schema 13's breakpoint evidence and schema 12's paused-start/control evidence. [Start paused, Step and Continue](control.md) share SDK/CLI/HTTP/preview-protocol/release logic, checkpoint guards, durable request identities and optional per-run node breakpoint configuration. Old runs and their checkpoint hashes remain valid; global execution limits and uncertain-attempt restrictions are not reset. Experimental live-page stepping controls retain pending control metadata and submitted breakpoint lists across refresh. Graph selection, local drafts and recorded-hit labels have serialized controller/graph tests; cooperative Pause uses the same retained control ledger and stops before the next node without aborting the current one. The HTML Request Pause/Retry controls retain a separate exact UUID/guard, reconcile through reads only, and re-read after overlapping responses to avoid stale status. Real-browser debugging qualification remains unfinished.

`exportRun(id, includePrivate?)` and `runs export` produce bounded read-only [run evidence](evidence.md), with default payload/actor exclusion, stable snapshot SHA-256 and explicit private opt-in. Owner HTTP, preview-scoped protocol and exact-release launchers share this implementation. The consistency guard retries reads if validation overlaps a transition; it never resumes execution. This is not test-result packaging, a restore format or independently signed evidence.

Saved cases, schema-derived candidate generation and expected/actual inspection are described in [testing.md](testing.md). `src/testing` owns versioned definitions, acceptance history, bounded generation and pure evaluation of retained results. Schema 8 added case history and optional run-to-case provenance; schema 9 adds atomic generation batches with immutable receipts. Schema 11 adds imported-case provenance for opt-in v2 project JSON/ZIP transfer. Old evidence is preserved. Imports remap cases as locally attributed drafts, retain source identity/hash claims and commit atomically with the new project. The direct SDK/CLI and authenticated JSON API share this implementation. Generation and transfer never accept or execute drafts. [Reviewed suites](suites.md) use saved manifests and existing guarded test operations through `@jevable/core/testing`, direct CLI or the selected management service. Serial remains the default; optional reviewed concurrency 1–8 bounds parallel calls per invocation, preserves result order and awaits every admitted peer when admissions stop. The HTTP suite host pins the owner before dispatch. There is no database schema change, automatic approval or redispatch. The experimental preview uses the same core for project-scoped saved-case controls. Scheduled/distributed suites, suite-level telemetry and actual browser qualification remain pending; artifact/deployment qualification has its own scope.

For project creation, proposals, acceptance/rejection, duplication, archive/restore, guarded deletion and generation-pinned execution, use the CLI/SDK documented in [projects.md](projects.md). SQLite schema 4 adds deletion receipts; old project, run and provider records are retained during migration.

JSON/project ZIP transfer is documented in [transfer.md](transfer.md). `src/packages/project-zip.ts` creates a fixed allowlisted archive and reads it without filesystem extraction. Schema 5 admits import provenance events while retaining existing records; optional earlier history is explicitly external evidence. Version `0.1.0-alpha.1` is still pre-publication; downgrade to earlier development snapshots is unsupported.

Import `LocalRuntime` from `@jevable/core/runtime`, call `LocalRuntime.open({ dataDirectory })`, then `run(yaml, input, { id })`, `show(id)`, `events(id)`, `decide(id, attemptId, action, authenticatedActor)` or `close()`. The default model adapter uses this core's configured connections and credentials. `configureConnection`, `setCredential`, `credentialStatus`, `connections`, `providerAudit` and `check` expose the same setup/readiness functions as the CLI; see [providers.md](providers.md). An explicitly injected SDK adapter may replace the default and must implement admission, durable request/response execution and side-effect-free evidence verification. Unknown providers, missing credentials and disallowed models are rejected before creating a run.

Await asynchronous SDK operations, including `check` and retained-evidence reads, before changing provider configuration or closing the owner. Configuration/credential changes and `close()` return `busy` while these operations or executions remain pending; close does not cancel them. Explicit `telemetryFlush()` also prevents credential/configuration changes, but close may join those exports through the bounded telemetry shutdown. Once close is admitted, all new SDK work is refused as `closed` before telemetry/storage shutdown. Repeated close waits for the same cleanup result, and storage ownership is released even if telemetry shutdown fails. `telemetryStatus()` remains readable for final diagnostics. These guards cover this runtime instance, not independently mutated injected adapters or a shared PostgreSQL runtime that has not yet been integrated.

The private directory must have mode 0700 on POSIX; the database and owner lock are 0600. SQLite commits each intent and each settled checkpoint with its corresponding evidence event. Node's built-in SQLite module may emit an experimental warning on supported Node versions. No server or Docker is needed for this mode. This is single-process ownership, not distributed execution or an exactly-once guarantee.

A run left in `executing` after failure means intent was saved but settlement is uncertain. Reusing its run UUID returns that state; `resume` refuses it. A safe `paused` checkpoint can be explicitly resumed. Opening, inspecting or listing never resumes work. Approval decisions commit actor/action/time and the continuation together; a stale or already consumed attempt is refused.

An abrupt process exit leaves `runtime.lock`. This build deliberately does not delete it based on PID guesses. For explicitly authorized recovery or completion of an interrupted transaction, read [owner recovery](owner-recovery.md) for the exact commands, proof requirements and refusal boundaries. Neither operation opens SQLite or resumes work. Unsupported or incomplete evidence remains blocked; never silently clear a lock or barrier. Preserve the database and journals, and inspect pending runs after separately authorized startup.

HTTP SIGINT/SIGTERM drains admitted work and releases storage; timeout reports ongoing drain rather than forcibly interrupting execution. Direct SDK-owned CLI jobs and exported-app jobs also retain the first signal through owner startup, admitted work and cleanup; they stop further dispatch, emit a draining diagnostic, and return 130/143 after closing. Repeated signals never force termination, cancel a run, clear a lock or replay a request. Remote/Docker clients do not acquire owner shutdown authority; suite/watch/service commands retain their separate lifetimes. See [job shutdown](job-shutdown.md). Explicit [cancellation](cancellation.md) persists a request before cooperative abort and retains the stopped checkpoint/uncertain attempt. Schema 10 adds its state and journal validation. Schema 15 adds explicit [retained-model settlement recovery](control.md#recover-an-already-saved-model-response) with guarded control identities; it never repairs a stale lock or dispatches an uncertain request. Automatic recovery, broader crash-lock platform/artifact qualification, interrupted-recovery completion, forced-termination qualification and unknown-provider-outcome reconciliation remain pending.

Exit codes: 0 completed/read or cancellation-submission success, 1 operational failure, 2 invalid command/input, 3 waiting/paused, 4 workflow failure, 5 uncertain dispatch, 7 cancelled execution; saved-test execution uses 6 for a terminal expectation mismatch (see [test outcome semantics](testing.md)). Cancellation submission success is not proof the run stopped. CLI receipts exclude private intermediate payloads; `approvals show` intentionally returns the saved review input to the local owner. Optional [OTLP HTTP/protobuf or gRPC traces, metrics and logs](telemetry.md) use private SDK providers, bounded exporters, persisted segment/node contexts, fixed metric labels and allowlisted structured end events. HTTP/protobuf remains the default; gRPC requires an explicit protocol and origin-only URLs. Metric/log export does not reconstruct observations from old runs. The optional [local development observability profile](observability.md) supplies backend/dashboard/alert examples. Scheduler backlog, complete retry/recovery accounting, full API/access/journal instrumentation, browser dashboard review and production deployment observability remain pending.

The root package remains private and unlicensed for publication while distribution terms are decided. Required MIT notices for copied harness code are retained separately.

## Release runtime build

For embedded applications, [durable asynchronous SDK admission](async-runs.md) separates acknowledged run creation from this invocation's execution promise on both hosts. It reuses the existing evaluator, journal and lifecycle guards, without a detached queue or automatic resume. Explicitly enabled owner HTTP/CLI and exported-app submission support `202` with an exact relative Location, retained observation and server drain of admitted work. The client never silently retries or resumes a run. Actual PostgreSQL, interruption, image and production qualification remain profile-specific; neither SDK support nor an HTTP receipt proves those broader gates complete.

The bundled app now has exact-release local `token/serve/status/request` operations in addition to direct CLI jobs. `ReleaseSession` narrows the shared HTTP transport to a strict source-free operation set and filters every retained-run operation by release ID/hash/revision. Each request carries the reviewed release hash; the app client supplies its verified package identity. No authoring, preview, provider or credential mutation is exposed. The exported app verifies actual runtime bytes; a trusted SDK service host remains responsible for code attestation. See [release service](releases.md#serve-the-exported-app). Direct HTTPS is available with separately provisioned certificates and explicit origin/address configuration; local and actual host-loopback Docker checks have separate qualification records. They do not establish public ingress or Kubernetes behavior.

`npm run build` also bundles `src/releases/entry.ts` and its dependencies into `dist/release-runtime.mjs`, with build metadata and dependency notices. Only Node builtins may remain external; no harness/source-checkout import is allowed. The build-only esbuild dependency is not required by installed or exported apps. See [releases.md](releases.md) for immutable release snapshots, SDK/CLI export and independent app execution. Schema 6 retains release snapshots and run provenance.
