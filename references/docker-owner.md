# Local and Docker runtime ownership

Use this for explicit runtime startup and lifecycle operations. The deployed process is the **Jevable workflow runtime**, not a skill runtime. The SDK is `@jevable/core/docker`; importing it starts nothing. Local SDK jobs and the default foreground service require no Docker, Jarness, desktop or parent checkout.

## Local default

`runtime start --token-file <private-token> --data-dir <private-state>` is an alias for foreground `runtime serve`; `--runtime local` is optional. It keeps the existing SQLite/PostgreSQL, TLS and SIGINT/SIGTERM drain contracts. It does not install a background daemon or discover another app. Local process stop/restart remains under the invoking process manager, not the Docker owner commands below.

## Start an owned Docker service

First build and review a [management image receipt](management-images.md). A release-image receipt is not interchangeable. Provision an independent private token (`runtime token`) and a certificate/private key for `127.0.0.1`; certificate issuance is not automated. Use a private parent directory for the owner record and credential files.

```sh
jevable runtime start --runtime docker \
  --image-receipt management-image.json --receipt-sha256 <reviewed-receipt-file-hash> \
  --owner-file /private/jevable/owner.json --port 8787 \
  --token-file /private/jevable/token \
  --tls-cert-file /private/jevable/server.crt --tls-key-file /private/jevable/server.key \
  --ca-file /private/jevable/ca.crt --wait-ms 20000
```

The image receipt selects the explicit local Unix-socket Linux Docker context, platform and immutable image. Startup never builds, pulls, pushes, loads an archive or falls back to local. It requires the host Docker CLI. A container must never receive the host Docker socket to call this launcher recursively.

Before Docker mutation, startup atomically writes and syncs an owner record containing the image receipt, random owner UUID, resource limits, host port and certificate fingerprint. It contains no credential values or local credential paths. Publication refuses an existing record—even when a previous startup failed. Retain its path and SHA-256 from the result (or an error carrying `owner`); these are consistency checks, not a signature or independent peer-certificate attestation.

SQLite startup allocates two fresh, uniquely named and labelled local volumes: writable workflow state and private service configuration. PostgreSQL uses only the configuration volume and an explicitly selected external database. A non-root, network-disabled initializer receives token/certificate/key and optional database configuration via bounded stdin, never arguments or environment. The service mounts configuration read-only, runs as `node` with a read-only root filesystem, drops capabilities, disables privilege escalation and publishes only `127.0.0.1:<port>`. Default limits are 512 MiB, one CPU and 256 PIDs; memory/CPU options are bounded. Default networking uses Docker's `bridge`, so outbound access is possible; this is not an egress sandbox. No workflow is submitted by startup or readiness checks.

This owner profile defaults to SQLite and serves a JSON-only management API. PostgreSQL is an explicit alternative below. Normal CLI commands can select that owner as described below; `runtime request` and `runs watch` also accept its explicit HTTPS endpoint. Provider credentials/configuration must be provisioned independently. Container loopback is not the host; external provider/OTLP connectivity is not qualified by deterministic lifecycle tests. This launcher does not accept arbitrary mounts, host/shared-container/overlay networking, public ingress, service-token/TLS rotation or image replacement. HTML uses the separate preview gateway, not an additional page in the management service.

### Optional asynchronous run admission

Add `--async-concurrency 1..64` at startup (SDK: `asyncRuns: {maxConcurrentRuns: 2}`) to enable the existing owner-only asynchronous API. Use one integer, not the literal range. Omission preserves disabled routes and older owner records. The strict policy is validated before file access, Docker calls or owner publication and saved in the private owner record; the service receives only `--async-concurrency <reviewed-capacity>`. No new configuration file, queue, scheduler, skill runtime or desktop service is involved.

Authenticated inspection/readiness verify that the exact service command and advertised capacity, metadata-only receipts, required owner/instance authority, reviewed release pins, no-replay admission and no automatic resume match the record before reading health. Health must report an integer `activeAsyncRuns` within the reviewed bound. Missing, changed or unexpectedly enabled policy leaves readiness unproven; the launcher never removes an option, silently upgrades an image or replaces the owner.

Use [explicit submission/observation](async-runs.md#explicit-cli-submission-and-observation) with the inspected HTTPS endpoint, current instance, protected owner token and trusted CA. Retain the run UUID and strict request file first. A `202` is acknowledged durable creation, not completion. Read-only metadata inspection does not execute or expose private results. Ordinary synchronous authoring/run/test commands remain available; async admission is an explicit alternative, not an automatic conversion of every run.

Clean restart reuses the exact policy and container; inspect/stop/restart and ordinary commands refuse startup overrides. SIGTERM drains admitted background work before releasing storage. A running or draining process is not stopped, and restart never resumes persisted intent. Select a reviewed management image built with this option. Source lifecycle/CLI tests cover both backend configurations with Docker-command doubles, not actual SQL/container/background-drain or broader deployment qualification of the updated image.

### Optional HTTP request-rate policy

Add `--rate-limits-file /private/rate-policy.json` at Docker startup (SDK: `rateLimitsFile`). Use the strict [two-bucket policy](rate-limits.md): a regular owner-only, non-symlink UTF-8 JSON object, at most 4096 bytes. Validation happens before Docker access or owner publication. Omission keeps existing owners unchanged and disables rate limiting; no account, provider, desktop or harness policy is discovered.

The network-disabled initializer receives canonical validated JSON through bounded stdin, writes `/config/rate-limits.json` as `0600`, and the service reads it from the read-only configuration volume. The private owner record stores only `rateLimits.sha256`, not the host path or policy values. Inspection/readiness require the advertised policy, algorithm, scope, reserve authority and no-automatic-retry/nonpersistent semantics to match. Missing, changed or unexpectedly enabled policy fails readiness without replacing the container, removing the option or accepting another image.

Clean restart retains the exact staged policy and works without the original host file; restart/inspect/stop and ordinary commands reject policy overrides. Restart creates a new service instance and resets local credit, so never use it to evade a quota. A health GET uses bounded control credit. If it is exhausted, readiness returns `starting` with `service.status: unavailable`, code `rate-limit` and an available `retryAfterSeconds` hint instead of automatically polling or restarting. Docker metadata-only inspection and exact-container SIGTERM stop do not need HTTP quota. Neither a running container nor a rate-refused health read proves readiness or workflow completion.

Source lifecycle tests cover staging, identity checks, refusal and restart for SQLite and PostgreSQL; they are Docker-command doubles, not actual container/database qualification of this feature. Select a reviewed image built with rate-policy support. Existing historical image receipts do not automatically qualify updated runtime bytes. Distributed/account/provider quotas and production/cluster deployment remain separate.

### Optional shared PostgreSQL HTTP quota

For two independently owned management services sharing request/control credit, select `--rate-coordinator-file /private/shared-quota.json` at Docker startup (SDK: `rateCoordinatorFile`). Follow the complete [PostgreSQL quota configuration](postgres-rate-limits.md): a regular owner-only non-symlink UTF-8 file at most 65,536 bytes, an already provisioned scope/policy, `initialize:false`, and container-reachable verified-TLS database identity. Docker refuses loopback-test TLS and refuses combining this option with `--rate-limits-file`, before token access or Docker mutation. Workflow storage remains a separate SQLite or PostgreSQL selection; never share a single-owner workflow journal to share quota.

The network-disabled configuration initializer receives normalized JSON through bounded private stdin and creates `/config/rate-coordinator.json` as `0600`. The service reads it from the read-only configuration volume. The owner record contains its canonical SHA-256, scope UUID, policy SHA-256 and admission deadline, not credentials, connection values or host paths. The service alone attaches to the separately provisioned backend; the launcher never creates a database, role, scope or quota sidecar.

Authenticated readiness checks the shared algorithm/scope/persistence contract and exact scope, policy hash and deadline before health. Missing, local-only, mismatched or unexpectedly coordinated capabilities do not prove readiness and never trigger policy removal or owner replacement. A quota refusal or unavailable coordinator stops readiness polling; inspect the retained owner/backend rather than automatically retrying uncertain admission.

Clean stop/restart uses the exact same container and staged configuration even if the original host file is absent. It never resets shared credit, initializes a scope, changes connection settings, refunds, replays or resumes work. Lifecycle commands and ordinary owner-selected commands refuse this startup override. Select a newly reviewed management image containing the feature; earlier images are not upgraded automatically. Source tests use Docker-command doubles and do not qualify actual container/SQL/received-OTel/cluster execution.

### An existing PostgreSQL workflow database

The Linux-arm64 fixture is covered by source-checkout receipt `qualification/docker-owner-postgres.json`: 52 checks per OTLP transport and 45 SQLite compatibility checks. These are standalone package/container and preview-protocol checks, not browser or production PostgreSQL qualification.

Add `--storage postgres --database-file /private/jevable/database.json` to the startup command. In the SDK, use `storage: 'postgres', databaseFile: '...'`. Select a separately provisioned PostgreSQL 17 database using the [private configuration contract](postgres.md). This launcher does not install PostgreSQL or create a database, role or peer container. `initialize: true` explicitly permits Jevable schema/namespace initialization within that selected database; use only with authority to initialize it.

The file must be regular, owner-only, non-symlink UTF-8 JSON, at most 320,000 bytes. Docker startup requires `tls.mode: 'verify-full'`, even for container-loopback addresses. The destination must be container-reachable and match its certificate; a private CA belongs in the database configuration, not the host management client's `--ca-file`. Plaintext/test-mode, missing or contradictory backend options fail before Docker access. No ambient PG configuration or SQLite fallback is used.

Validated normalized JSON is staged as `/config/database.json`, mode `0600`, in the read-only private configuration volume. The owner records only its SHA-256, not database host/user/password/namespace or host file paths. No SQLite state volume or host database directory is created. Readiness checks the actual PostgreSQL backend, reachable database and open owner session. A second owner cannot bypass namespace ownership; lost ownership is not automatically reconnected or repaired.

Clean stop retains records in the external database. Restart reuses the exact container and staged configuration without rereading the host database file, changing endpoints, resetting credentials or replaying waiting runs. Database backup, restore, migration, rotation and production availability remain separate operator responsibilities and qualification gates.

For selected-owner PostgreSQL commands, use `--page` with `runs list`, `tests list`, `tests generations`, `projects deletions`, `providers audit` and `releases list`; follow returned cursors. Do not repeat startup database flags on ordinary owner-selected commands. Release creation defaults to the selected owner's backend; explicit `--runtime-storage sqlite|postgres` changes only the exported app's backend, not the authoring owner.

### An existing private bridge network

For a collector or other explicitly configured service on a user-defined Docker bridge, add both `--network <existing-name>` and `--network-id <reviewed-full-id>` at startup. In the SDK, use `network: { name, id }`. Obtain and review these from the selected local Docker context; a network name alone is insufficient. This selects a network, not a database backend or a collector implementation.

The launcher checks the exact name/ID, local scope, bridge driver and non-ingress status before publishing the owner record. The owner retains that selection. The service joins by immutable ID, and observation/stop/restart verify the selected network and its sole container attachment. Configuration staging and SQLite credential jobs remain network-disabled. An explicitly requested PostgreSQL credential job uses the selected network to reach that database, without telemetry or workflow execution. Missing, renamed, replaced or additional network attachments are refused rather than repaired. The default is still `bridge`, including older owner records with no network field; `host`, `none`, shared-container namespaces and Swarm/overlay networks cannot be selected through this option.

Jevable never creates, connects other containers to, reconnects, removes or changes the selected network, nor does it provision its peers. Clean stop/restart preserves it. After network drift, inspect and explicitly resolve the deployment state; a new network using the old name is not the reviewed network. Docker administrator mutations can race metadata checks; network ID pinning prevents name-based replacement at launch but is not a security boundary against the daemon administrator.

Sharing a network grants network reachability to its other members, including this service's container port; host-loopback publication alone does not isolate peers. TLS, API authentication and Host/Origin validation remain required. Docker DNS aliases must match each destination certificate. Internal networks may restrict egress; this flag does not guarantee a firewall policy or a reachable provider. It never translates `localhost`, bypasses TLS or borrows another application's credentials. Use explicit HTTPS collector/provider URLs and independent credentials. Production network policy and remote/Kubernetes deployment remain separate qualification gates.

### Optional OpenTelemetry configuration

Add `--telemetry-file /private/otel.json` to **Docker startup**, using the explicit [OTLP configuration](telemetry.md). The file must be a regular owner-only non-symlink UTF-8 JSON object, at most 16,000 bytes. Unknown settings, invalid destinations, oversized or unsafe files are rejected before Docker access or ownership publication. Omission disables telemetry; no environment, harness or desktop settings are discovered.

For `authentication: {kind: "bearer", credentialRef: "otel/key"}`, SQLite requires `--telemetry-credential-file /private/collector-token`. PostgreSQL can instead use that reference already present in the explicitly selected database; supply the file only to provision a new reference. Provisioning requires generation zero and never overwrites an existing credential. This is a separate protected credential, not the management API token. The credential flag is refused for `none` or absent telemetry. Never place its value in the JSON, command arguments or environment.

The launcher normalizes the validated JSON and provisions it as `/config/telemetry.json`, mode `0600`, using bounded stdin to the existing non-root, network-disabled configuration initializer. The owner record retains its fingerprint and optional credential reference, not destinations, local paths or secret values. When a credential file is supplied, a separate short-lived CLI job initializes that reference via protected stdin before the service starts: network-disabled in the new SQLite state volume, or over verified database TLS for PostgreSQL. This does not execute a workflow. Failure retains the owner record/volumes for inspection; startup never repairs partial initialization or retries under a fresh owner automatically.

For a collector using a private CA, also select `--telemetry-ca-file /private/collector-ca.pem` (SDK: `telemetryCaFile`). This requires telemetry with at least one HTTPS destination, for either HTTP/protobuf or gRPC. The CA file must be a regular owner-only non-symlink UTF-8 PEM certificate bundle, at most 262,144 bytes; private keys, mixed content and invalid certificates are refused before Docker access. The initializer stages the exact bytes as `/config/telemetry-ca.pem`, mode `0600`. The owner records `telemetry.caSha256`, not the host path or certificate contents. The service alone receives `NODE_EXTRA_CA_CERTS=/config/telemetry-ca.pem`; initializer jobs do not.

**This adds process-wide Node TLS trust, not collector-only trust.** It may also affect provider HTTPS calls using default Node trust; it neither overrides explicit per-client CA settings nor enables mutual TLS. Review that scope before supplying the bundle. The existing `--ca-file` controls the host management client's trust only and is never reused as outgoing collector trust. Without the new flag, outgoing HTTPS uses the image's default Node trust. The owner rejects inherited `NODE_EXTRA_CA_CERTS`, `NODE_OPTIONS`, `NODE_TLS_REJECT_UNAUTHORIZED`, `SSL_CERT_FILE` and `SSL_CERT_DIR` overrides before publication, and checks the expected trust environment before lifecycle actions. Do not disable certificate verification.

The service reads the private configuration volume read-only and uses its own credential store. Clean restart uses those retained bytes, CA bundle and credentials; it does not reread host files. Runtime replacement/telemetry-destination/trust changes remain explicit operator work, not a `restart` side effect. Older owner records without a CA fingerprint still use the default-trust profile. Metadata checks/fingerprints are consistency guards, not protection from a malicious Docker administrator modifying volumes. Collector reachability and the selected certificate chain are checked during actual export, not by startup readiness.

`127.0.0.1` in a telemetry URL means this container's network namespace, not the host. Jevable does not start a Collector or translate endpoints automatically. Provision networking independently and authorize export of diagnostic metadata. Use authenticated `telemetry.status`/`telemetry.flush` through `runtime request` to inspect delivery; listener readiness does not prove collector reachability. Export failure never changes a committed workflow outcome or authorizes replay. Telemetry resource instance IDs are process identities, distinct from the management HTTP instance guard.

## Author, test and run through the selected owner

### Optional approval notification configuration

Add `--notifications-file /private/notifications.json` to Docker startup (SDK: `notificationsFile`). It uses the same strict [notification configuration](notifications.md) as a local owner: a regular owner-only, non-symlink UTF-8 JSON file, at most 100,000 bytes, with explicit destinations, credential references and bounds. It contains no signing key values. Validation happens before Docker access or owner publication. Omission disables new deliveries; no harness, desktop, environment or imported workflow supplies defaults.

The launcher stages normalized JSON as `/config/notifications.json`, mode `0600`, through the existing network-disabled initializer's bounded stdin. The service mounts that private volume read-only. The owner record retains only a `notifications.sha256` fingerprint, never receiver URLs, credential references, host paths or keys. No notifications are sent during startup, readiness, history reads or restart. SQLite and independently configured PostgreSQL use the same management routes and retained-receipt semantics.

For a receiver using a private CA, also supply `--notifications-ca-file /private/receiver-ca.pem` (SDK: `notificationsCaFile`). This requires at least one configured HTTPS notification destination and a regular owner-only non-symlink PEM certificate bundle, at most 256 KiB. It never disables hostname/certificate verification. The owner records its `notifications.caSha256`. When this flag is present, `/config/runtime-ca.pem` contains the notification CA plus any explicitly supplied telemetry CA, with telemetry first and a newline separator. `NODE_EXTRA_CA_CERTS` selects this file. Existing telemetry-only owners retain their original `/config/telemetry-ca.pem` behavior. The combined private staging payload remains bounded to 1,000,000 bytes; oversized inputs fail before owner publication.

Both CA options extend **process-wide Node TLS trust**, including compatible provider, telemetry and notification clients; they do not scope a CA to one hostname or receiver. Review both trust inputs before starting. A caller cannot inject arbitrary TLS environment settings, and lifecycle inspection refuses a changed service command or trust path. Fingerprints and container inspection detect configuration inconsistency, not a malicious Docker administrator rewriting staged files. Do not use these flags to trust an unreviewed destination or certificate.

Provision signing credentials separately through the selected owner's existing `credentials set <reference> --file <private-key-file> --expected-generation <reviewed-generation>` or protected stdin, using the owner selector below. Startup does not create or overwrite notification keys. Then use `approvals notify destinations|prepare|send|show|list` with that selector; sending still requires its reviewed request file and retained UUID. Never repeat `--notifications-file` on an ordinary selected-owner command. Container loopback means that container, not the host; receivers and networking must be independently provisioned. No recipient or network is automatically created.

Clean restart reuses the same staged configuration and protected credential store even when the host files are absent. It neither rereads host files nor rotates endpoints, resets keys, replays receipts or approves workflows. SIGTERM drains admitted sends; a `draining` result is not permission to force-kill or resend. Exact-release notification APIs and Kubernetes deployment configuration remain separate from this management-owner capability.

`projects`, `run`, `runs` (except the separately endpoint-based `watch`), `approvals`, `tests`, `tests suite run|result`, `check`, `providers`, `credentials`, `import inspect|project` and `releases list|show|create|export|build-image|export-kubernetes` accept the same owner selection:

```sh
jevable run workflow.yaml --input input.json --id <retained-run-uuid> \
  --runtime docker --owner-file /private/jevable/owner.json \
  --owner-sha256 <reviewed-owner-file-hash> --container-id <full-reviewed-container-id> \
  --token-file /private/jevable/token --ca-file /private/jevable/ca.crt
```

Use that selection with ordinary `projects create|propose|accept|run|export`, saved-test commands, `tests suite run|result`, `runs show|events|export|step|continue|cancel`, approval decisions and provider setup. Source, input, definition and protected secret files are read on the host and submitted over verified HTTPS; exported project/evidence artifacts are written on the host. No checkout or host file mounts are added to the workflow container. Local remains the default and accepts `--runtime local` for these commands.

The caller verifies the owner record, full container ID, Docker configuration and authenticated readiness, then pins the actual runtime instance for its requests. The service advertises `api.instanceGuard: x-jevable-instance` and rejects a changed instance **before dispatch**. Older images without that capability are refused; rebuild an explicitly reviewed image rather than bypassing the guard. A clean restart changes the instance ID, so a fresh CLI invocation must inspect the owner again. A wrong owner, stopped service or failed handshake never starts/restarts a container, opens host storage, repairs a lock or falls back to local execution.

Do not combine ordinary Docker-selected commands with `--data-dir`, `--storage`, `--database-file`, `--telemetry-file`, `--notifications-file` or an overriding `--endpoint`. Telemetry and notification destinations are selected at owner startup above, not per request. Each call defaults to a 30-second HTTP timeout (`--timeout-ms` can select 1–3600000). Timeout or response loss does not cancel the server operation. Preserve the original run/control/review identities and inspect them; never generate a new run ID merely to retry uncertainty. Docker `run` and `projects run` require an explicit `--id`; saved tests and suite manifests already retain their run IDs. Commands preserve workflow/test exit codes, unlike generic `runtime request`'s HTTP-success exit code. Actor attribution is fixed by the service, not supplied by the host command.

Tests and suites perform real execution, stop on their documented pending/uncertain states and never automatically approve. Provider `credentials set --file|--stdin` still protects secret input; values are submitted only to the selected owner and omitted from receipts. Configuring a provider is not proof of external connectivity. Read-only inspection/evidence export neither executes nor resumes a workflow. `preview --serve --runtime docker` uses this selector through a separate loopback gateway; read [live preview](live-preview.md#preview-through-a-selected-docker-owner). Require a distinct preview token and retained project UUID. The browser never receives the management token; closing the gateway leaves this owner running. Browser qualification remains open. Project export is a transfer bundle, not a runnable release.

Docker `import project` and `releases create` also require retained `--id` values. Read [transfer](transfer.md#optional-docker-owner) for host-side archive validation and draft test import, and [releases](releases.md#optional-docker-authoring-owner) for exact host/server runtime matching. The selected owner retains metadata while ZIP/image/Kubernetes packaging runs on the host; no Docker socket or checkout mount is added to the owner. Older management images without the new release operations must be replaced through an explicitly reviewed operator procedure, not silently upgraded by a command.

## Inspect, stop and restart

```sh
jevable runtime inspect --runtime docker \
  --owner-file /private/jevable/owner.json --owner-sha256 <reviewed-owner-file-hash> \
  --token-file /private/jevable/token --ca-file /private/jevable/ca.crt
jevable runtime stop --runtime docker \
  --owner-file /private/jevable/owner.json --owner-sha256 <reviewed-owner-file-hash> \
  --container-id <full-reviewed-container-id> --wait-ms 20000
jevable runtime restart --runtime docker \
  --owner-file /private/jevable/owner.json --owner-sha256 <reviewed-owner-file-hash> \
  --container-id <full-reviewed-container-id> \
  --token-file /private/jevable/token --ca-file /private/jevable/ca.crt
```

Inspection is read-only. Without the optional token it checks Docker metadata only; it does not prove service readiness. With credentials, it verifies HTTPS, API version/backend and matching capabilities/health instance identity. It checks the owner labels, selected container configuration, limits, mounts and port before operating; metadata mismatch is not repaired. An absent container does not mean its volumes are absent.

Stop requires the exact full container ID, sends **SIGTERM only**, and observes shutdown. It never escalates to SIGKILL, cancels a workflow, removes a container/volume or clears a lock. `draining` means the process is still running, not that shutdown completed. Inspection remains available after a timeout. A clean exit must have exit code zero without OOM termination.

Restart reuses that exact container only after a clean exit. If already running, it observes readiness without interrupting it. It refuses created, paused, restarting, dead, OOM or uncleanly exited owners; it does not recover stale locks, replace images, rotate files, approve or replay retained workflows. A new runtime instance ID after restart is expected; persisted run identities and waiting approvals remain unchanged.

For start/restart, exit zero means readiness was observed; for stop, it means clean shutdown was observed. Exit 8 means the requested ready/stopped state was not proven (for example starting, draining or unclean exit); read the status, do not retry mutations blindly. Inspection exits zero for a valid observation, including absent/exited or unavailable-service status. Operational failures exit 1; CLI usage errors exit 2. `--wait-ms` bounds the polling window (0–60000); individual bounded Docker/HTTPS checks can extend elapsed time beyond it.

## Interrupted or failed startup

Resources may exist even when startup returns an error or the CLI was interrupted. Inspect the persisted owner record and selected Docker context before doing anything else. Lost `docker run` acknowledgement does not justify a new owner. Configuration initialization may be partial; there is no automatic adopt, resume-start, force cleanup or replacement operation. Keep partial resources for explicit operator assessment. Resource names/labels protect against accidental targeting, not a malicious Docker administrator; the daemon and reviewed image are trusted.
