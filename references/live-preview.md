# Live workflow preview — experimental

Use this for an explicitly requested local HTML testing session. It runs the standalone Jevable workflow runtime, not Jarness or a desktop service. The protocol, installed CLI lifecycle and controller test doubles are tested; **full actual browser controls, layout, CSP enforcement and accessibility remain separate qualification**. Check the current host's exposed browser permission; serving a page never overrides a browser-policy refusal.

## Session access is not a live connection check

**Session open** means this tab has authenticated workspace access, not that the runtime is currently reachable or local. The separate reply status says **Last runtime reply verified**, **Waiting for a runtime reply**, or **Connection unconfirmed** using existing requests only; no background connectivity probe or automatic reconnect is added. A verified reply is historical, not a continuous health check. After a missing reply, check that the preview is running and explicitly refresh saved information, such as **Refresh list** in **Past runs**. An unrelated successful read updates connection feedback without dismissing an unresolved action warning, changing retained request identities or authorizing a retry. Failed status reads also preserve a more important unresolved Run/control warning; a successful same-run status read may replace a pending Run warning only after it finds that saved run. Expiry still requires explicit Connect; late replies from an older session/page/dispatch cannot restore the connection indicator.

**Past runs** owns the feedback beside **Refresh list**. A failed read keeps the last known list; a successful explicit read replaces that local warning with a fresh-list or empty-list message. Neither result dismisses a separate unresolved workflow, approval or control warning. Old replies cannot replace a newer read, selection, session or page context. Loading, success and failure here are read outcomes, not workflow execution or approval outcomes.

The default view keeps the run picker and refresh feedback visible. **Troubleshooting history** reveals optional model-attempt and approval-delivery controls; opening or closing it does not read, execute, clear filters or change authorization. Run labels use plain-language outcomes and short references, with full IDs for colliding prefixes. A run created by a saved test also says **saved test**. The option value and title retain the exact UUID, and selecting one still performs only the existing saved-run read. In **Saved tests**, expected-versus-actual inspection is available only when the selected run actually carries a saved-test identity; selecting a test definition alone or an ordinary run does not invent an assessment.

A retained `executing` status is labelled **Result not confirmed**, not proof that a worker is active now. A pending submission is **Request not confirmed** and may already have been accepted; a pending saved-run read is **Reading saved status** and may already have a recorded outcome. Inspect the same retained run before considering another submission. These labels do not poll, retry, start, resume or cancel work, and do not change the underlying status or controls.

## Keyboard and loop navigation

The left-to-right graph shares [portable keyboard navigation](preview.md): Tab or arrow keys move focus, Enter/Space opens step details, and Escape returns to the background for pan/zoom. Moving focus does not select a run/node, inspect private values, check readiness, run, approve or resume. **Fit graph** is an overview and may shrink labels on a narrow screen; choose **Read steps** to inspect each node at readable scale, then use **Earlier** and **Later**. Loop exploration has a **Back to workflow** action that restores focus to its parent loop. Existing exact-scope selections and private-inspection fences still apply when you explicitly open details.

The workspace's keyboard skip link goes to the private key field before connection, or to the actual graph afterward—even when another workspace page is open. Only activating that link moves focus; connection and status refresh never activate it or run anything. Focus styling and serialized-controller/React DOM tests are implemented, but native browser/screen-reader/enforced-CSP/responsive/no-guidance acceptance and real GIFs remain open.

## Start a session

From the built or installed skill directory:

```sh
node bin/jevable.mjs runtime token --output .jevable-http-token
node bin/jevable.mjs preview examples/approval.yaml --serve --token-file .jevable-http-token --data-dir .jevable-preview
```

Token creation refuses an existing destination. Reuse an existing private token file when appropriate; do not overwrite it or print its contents in chat. The readiness receipt reports the actual loopback URL, instance ID and pinned preview project. An optional `--port` selects a port; `--runtime local` is the default. Docker uses the separate gateway described below, never an automatic fallback. The CLI does not open a browser itself: the agent should use the host's browser tool as described below. `--output` instead produces [offline HTML](preview.md) and cannot be combined with runtime options.

Missing or malformed pasted keys are refused locally with an inline correction and no request. A valid-shaped key rejected by bootstrap has a separate **access key was not accepted** message; choose the key for this exact workspace. These messages also apply after expiry, without discarding retained run/control identities or retrying authentication automatically. Transport failures remain separate, sanitized connection errors. No key or upstream error text is echoed in the message.

## Reopen an existing project without creating or running

For a retained project, review its current `id`, `generation` and `acceptedRevision` through the explicitly selected owner. Save a strict JSON pin with exactly `id`, `generation` and `revision` (the accepted revision), and review the SHA-256 of that exact file. `schemas show preview-project-pin --json` describes the input. Use workflow source whose compiled revision matches it.

Add `--project-pin-file <reviewed-pin.json> --project-pin-sha256 <reviewed-file-hash>` to a `preview <workflow.yaml> --serve` invocation. These flags replace `--project-id`; do not supply both. Direct SQLite/PostgreSQL previews and selected Docker/HTTPS gateways support the same explicit attachment:

```sh
jevable preview reviewed-workflow.yaml --serve \
  --endpoint https://reviewed-workflow-owner.example \
  --instance-id <reviewed-current-owner-uuid> \
  --token-file <private-management-token> --ca-file <reviewed-ca.pem> \
  --preview-token-file <distinct-private-preview-token> \
  --project-pin-file reviewed-project.json --project-pin-sha256 <reviewed-pin-file-hash>
```

The bounded regular pin file's exact checksum, strict shape and source revision are checked before target credentials or storage. Startup only reads `projects.show`; it requires the same active project, current generation and accepted revision. It does not create, accept, restore or execute. Archived, missing, changed or malformed targets fail, with no fallback. Existing run/test scopes retain the exact project generation/revision; this does not broaden a viewer to all historical generations.

After runtime replacement, the old gateway remains pinned to its original runtime instance and refuses; it never reconnects automatically. Explicitly review the new owner instance and start a new gateway with the same unchanged reviewed project pin. Retained runs/approvals can then be inspected in their original scope, without recreating the project or replaying a run. A changed generation/revision requires a new review, not automatic pin refresh. An uncertain startup read is observation-only but still has no automatic retry.

Fresh preview creation remains the default when no attachment is selected. A creation conflict never switches to attachment implicitly. Gateway shutdown still owns only the local viewer, not its remote runtime or storage. Local protocol/SDK checks are distinct from installed, actual browser and Kubernetes attachment qualification.

## Automatic local connection

For a direct local preview, `--token-env VARIABLE_NAME` reads exactly one explicitly named environment variable containing 64 lowercase hexadecimal characters. It is mutually exclusive with `--token-file`. Missing/invalid values fail before runtime storage opens; errors do not include the value. Environment selection alone does not log the browser in. The CLI does not load, discover or write `.env` files; your launcher may supply one (for example `node --env-file=.env bin/jevable.mjs ...`). Protect that file and never commit credentials.

Add `--auto-connect` to avoid key entry in the browser:

```sh
node bin/jevable.mjs preview examples/approval.yaml --serve --token-env JEVABLE_PREVIEW_TOKEN --auto-connect --data-dir .jevable-preview
```

You can also use `--auto-connect` with the existing protected `--token-file`. Both new options are supported only for direct local preview (SQLite or explicitly configured local PostgreSQL), not a Docker/remote-owner gateway, exported offline HTML, TLS or a non-preview runtime server.

This is an explicit **local-machine trust mode**, disabled by default. Other processes on the same computer can acquire access to this preview project, including its private workflow data and scoped run/decision operations. Do not enable it on a shared/untrusted machine. Loopback Host/peer checks, exact required Origin and instance headers, Fetch Metadata checks, JSON-only POST, bounded sessions and existing CSP reject cross-origin browser requests, but cannot authenticate local processes that forge those headers. The management API always requires its owner token. The owner key is never embedded in HTML, URLs, receipts or browser storage; only the one-hour project-scoped session is returned. At most eight active sessions exist per server instance.

Browser request-origin defenses use [Fetch Metadata](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Site) alongside exact Origin and a custom instance header, consistent with [OWASP's CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). These browser guards do not turn localhost into an authenticated boundary against local applications.

Opening performs bootstrap and read-only view/history requests, never Run, acceptance or approval. Refresh reuses an unexpired tab session. Disconnect revokes that session and suppresses automatic connection on refresh; choose Connect explicitly to reconnect. Failed connections do not retry automatically. A new server instance invalidates previous sessions. This changes authentication convenience, not workflow authorization or project/revision guards.

When a session expires or a scoped request is refused as unauthorized, the viewer closes its connected view, disables runtime controls, clears private result/review displays and asks you to reconnect. No operation is retried. The expiry deadline is checked while the page is open, before a request, and when returning to it. An expired or refused session stays marked as requiring an explicit **Connect**, even after reload; automatic-local mode needs no key entry for that click. Manual mode requires its protected key again. Saved run/case/batch, cancellation and pending control/Pause identities stay retained for this same instance/project; reconnect reads them without executing, approving, retrying or changing their guards. Late old-session responses cannot restore values or affect the new connection. A new server instance still requires its own freshly reviewed preview, not automatic retargeting.

A submission refused before network dispatch is explicitly unadmitted and retains its UUID for inspection. A server refusal alone is not absence proof: reconnect checks the original run before marking it unadmitted. An uncertain identity without a definitive refusal is never discarded merely because a read cannot find it. If tab storage or retained identities are unavailable/corrupt, inspect through the owner API; do not create a replacement run to bypass uncertainty. These behaviors have serialized-controller/DOM tests; real-browser expiry and reconnection acceptance remains separate.

### Preview with PostgreSQL storage

Local preview defaults to SQLite and needs no database server or Docker. To explicitly use your separately provisioned PostgreSQL database, prepare the private configuration described in [postgres.md](postgres.md), retain a fresh project UUID, and run:

```sh
node bin/jevable.mjs preview examples/approval.yaml --serve --storage postgres \
  --database-file /private/jevable-database.json --token-file /private/jevable-http-token \
  --project-id <retained-fresh-project-uuid>
```

The process owns that database namespace; it never creates a SQLite directory, starts Docker, discovers another app's database or falls back. The readiness receipt reports `storage: postgres` and the exact project identity. Set providers before starting, or use the owner's authenticated management API. `--telemetry-file` and `--trace-viewer-file` are explicit optional configuration, not credentials supplied by the page. The same scoped tests, approval, breakpoint/Pause, evidence and trace-navigation protocol is used; browser qualification remains open.

This HTML listener is loopback HTTP only. Database TLS is independently configured in the private database file. Combining SDK preview with web-service TLS or an exact-release snapshot is rejected; it does not expose a cluster viewer or add HTML to release-only apps. The SDK entry point is `startPostgresRuntimeService({runtime: {database, telemetry?}, token, actor, preview: {source, projectId, traceViewer?}})` from `@jevable/core/http/postgres`. For explicit attachment, replace `projectId` with the strict reviewed `projectPin`; never supply both. Sources/options are validated and cloned before database ownership; fresh project creation or the selected guarded project read occurs only after the listener binds.

Fresh startup can commit a project even if acknowledgement is lost. Inspect the retained project UUID with the owner API or, after shutdown, direct PostgreSQL commands. Do not generate replacement identities automatically: reusing an already committed creation ID conflicts, never silently attaches. Default startup creates a fresh project; an explicitly reviewed `projectPin` instead reopens its exact retained scope without creation. Every new preview invalidates prior tab tokens. Loss of database ownership fails closed and never reconnects automatically.

SIGINT/SIGTERM during startup is remembered: once startup finishes the service drains without emitting a misleading ready receipt. Shutdown waits for admitted work and emits a final `closed` receipt. It does not roll back project creation or cancel external effects. These lifetime guards also apply to SQLite preview and the Docker gateway; closing the gateway still leaves its remote owner running.

## Project notification history

The experimental **Approval notification history · read-only** panel explicitly loads one page for the preview's retained project ID, historical generation and workflow revision. It is available after connection without selecting or starting a run. **Load / restart history** reads the first 25 identities; **Read next page** follows the returned cursor. There is no background polling, automatic load or notification dispatch. UUID order is not event-time order; pages are live keysets, not an atomic snapshot. Restart the traversal explicitly to observe earlier inserted IDs or updated settlements.

The scoped preview operation is `{operation: "notifications.list", page: {after?, limit?, filter?}}`. The page object is required and limits are bounded to 1–200. The optional strict filter has `outcome`, `eventKind`, `createdFrom` and `createdBefore`; see [history filter semantics](notifications.md#read-only-outcome-lifecycle-and-creation-time-filters). The server supplies the retained project pin to the owner's `notifications.project-list`; callers cannot supply a different project, run or actor. Replies must echo the canonical filter and match it, that pin, row revisions, metadata schema, identity ordering and cursors. An older or unsupported owner fails without an owner-wide or unfiltered fallback. Renaming or editing the owner project does not silently change the historical scope.

Choose an outcome/lifecycle kind and optional exact UTC ISO millisecond bounds in **History filters**. From is inclusive and Before exclusive, using delivery creation time rather than event/settlement time. Editing only stages a draft; **Load / restart history** applies it explicitly and begins at the first matching UUID. The displayed summary names the applied query. **Read next page** uses that same query and is disabled while the draft differs or is invalid. Invalid input does not read or discard an existing displayed page. Editing during a pending read invalidates its late reply without starting another request. ## Input fields and JSON

Exported JSON has a separate checksum for destination import review. Selected options, evidence changes, disconnect and pagehide invalidate pending downloads and revoke object URLs. ## Runnable release ZIPs

The experimental **Deliver a runnable workflow app** panel uses the same owned core release packager as the CLI. Choose a version and explicit SQLite/PostgreSQL app backend, optionally enter plain-text **Release notes**, then **Create pinned release**. This creates an immutable release for this preview's exact project/generation/revision; it does not run the workflow or build/deploy an image. PostgreSQL authoring can export a SQLite app and vice versa. Both ends of a Docker-backed preview must carry the same trusted runtime build; a mismatch is refused, never downloaded or substituted from Jarness.

To reopen an existing saved version in a fresh viewer, choose **Load saved versions**, pick a **Saved version**, then **Open selected version**. Only this exact preview project/generation/revision is shown. Listing and selection never create, package, download or execute. Opening reads and verifies the selected release/hash/runtime, then enables separate explicit ZIP preparation. An unresolved creation request must first be inspected, not discarded in favour of a different version.

The `release.list` preview operation scans one explicit 25-row owner metadata page per request. Source, notes, actors and run history are excluded from its reply. Matching candidates are re-read and validated before projection. Empty matching pages can still have a next cursor: choose **Read next page** until the list ends. UUID order is not version/time order, and pages are live observations, not one atomic snapshot. Opaque cursors hide other-project identities, remain only in this preview instance's memory, expire after fifteen minutes and are limited to1024 retained cursors; a traversal refuses above10000 examined rows. Expiry/refusal requires an explicit fresh Load, never automatic retry or broader history fallback. Runtime identities whose exact bytes are unavailable remain visible as **Original runtime required**, but cannot be opened/exported using substituted current bytes.

The page and selection remain in memory only and clear/fence late reads on session/scope changes, pagehide and disconnect. Pageshow does not load a list. A successfully opened version retains its ID/project/version/backend, optional plain-text notes and exact release checksum in this instance's tab-scoped request storage, so reload requires explicit **Check saved release** before packaging. Changing a draft selection cannot package the previously inspected version under the new choice. These protocol/serialized-controller checks do not establish actual browser saving, accessibility, layout or deployment qualification.

Creation retains its UUID, version, backend, project pin and optional note text in tab storage before dispatch. No workflow source, evidence bytes or configured credentials are automatically added to that record. A lost response leaves the UUID available for **Inspect retained release ID**, which calls only `release.show`; it never repeats creation or submits replacement notes. Reload restores the request/text, not a reviewed receipt or automatic request. If inspection remains unresolved, use the CLI against that exact owner/ID rather than inventing another request. **Prepare another version** is available after a successful receipt and unlocks the note draft without deleting the old release. Disconnect clears this tab's request record; copy its ID first if you need to inspect it later. The runtime retains the release independently.

An empty note editor omits the field, preserving the historical request/receipt shape. Nonempty notes must meet the [shared immutable note contract](releases.md#optional-immutable-release-notes): nonblank well-formed text, at most 16,384 UTF-8 bytes, and no ASCII controls except tab, CR and LF. The byte counter is informational; both the serialized page helper and server enforce the bound. Text read from the editor is retained unchanged in the request and hashed release; the browser may normalize pasted line endings before exposing the textarea value. Notes are displayed as plain receipt text, not interpreted as HTML. They are publishable in exported ZIPs/images and can persist in this tab, so exclude secrets and private run data. They never become workflow input or approval authority. Invalid retained text, changed owner notes or altered download metadata disable export rather than silently accepting a new review. Controller/protocol checks are not actual browser, layout, accessibility, storage or download qualification.

Review the returned project/release/runtime identities, then explicitly **Prepare runnable release ZIP**. `release.export` verifies the reviewed release checksum and resolves its exact installed runtime bytes. The default is an evidence-free runnable app. The ZIP includes source, bundled runtime, integrity-checking launcher, requirements, notices and Docker templates. Node 22.19+ is required; providers, secrets, persistent state and any PostgreSQL database must be configured independently. Packaging success does not prove target readiness. Source itself may contain inline secrets even when evidence is excluded.

The server rechecks scope and captures the same declared privacy; changed bytes cause a conflict and require fresh review, not silent substitution. Private evidence requires separate consent for each release preparation. Building the included Dockerfile also includes that private evidence in the image; no image is built or published by these controls. Attachments remain review-only and never restore runs/tests/approvals or prove execution of this release.

The page verifies the pinned release/runtime/project receipt, exact attachment checksum/privacy, canonical base64, byte count and ZIP SHA-256 before exposing a manual download link. `previewReleaseTools()` provides the same browser-safe receipt/download checks through `@jevable/core/preview`; it is not a ZIP parser or publisher authenticator. ZIPs are capped at 12 MB. Evidence changes, scope changes, disconnect and pagehide invalidate late downloads and revoke object URLs. Private consent is consumed at preparation. Actual browser download/CSP/accessibility qualification remains open; use CLI export for controlled file permissions and larger archives.

## What have your tests reached?

A report with unavailable reads says it is incomplete; missing legacy branch records stay unknown. A passing expectation for a waiting Human Approval does not mark that approval or its downstream step as completed. Counts are retained observations, not proof of correct results, complete paths or every condition.

The preview-only `tests.coverage-runs` command returns metadata for up to 100 most recently updated test-linked runs in the exact session project/generation/revision, with the scoped total count. It examines at most 10,000 underlying run rows and fails at the limit rather than silently claiming a complete list. For older selections, use [CLI suite coverage](suites.md#which-nodes-and-branches-did-these-tests-exercise). Inputs, outputs, case titles, actors, prompts and model answers are excluded. `tests.coverage` accepts only 1–100 unique run UUIDs. The server admits the entire selection before reading results, derives exact historical test identities from those runs and rechecks scope/test identity before each capture. Normal non-test and foreign/missing runs are refused. It never substitutes a newer case version, runs a suite, decides an approval or broadens the token to general management access. The shared standalone `testSuiteCoverage` SDK performs aggregation against the fixed workflow source.

Selections are kept only in the current page, not local/session storage. Clear, disconnect, session changes and pagehide drop selection/report; late replies cannot restore them. Reopening and selecting UI tabs do not load results automatically. To refresh observations, explicitly load, select and inspect again. The report's own selection does not replace the workflow's currently selected run or execution overlay. Per-run reads are not an atomic snapshot.

Source, authenticated loopback API and actual serialized-controller/DOM checks do not qualify real-browser layout, accessibility, CSP enforcement, no-guidance usability or demo GIFs. ## Saved tests in the preview

The Saved workflow tests panel operates only on the session's pinned project and revision. The server supplies that project and the authenticated owner actor; clients cannot override either. The editor accepts `title`, `input`, `expectations` and optional `triggerMode: "api"` as described in [saved tests](testing.md). Other mode values are refused. **Copy selected entry into unsaved case** changes only that draft and clears review consent; selection itself never silently edits a case. Loaded definitions preserve their mode. Omit the field for the default manual/chat contract. It never supplies arbitrary executable assertions. Save as new draft retains a case UUID before submission; Save edits appends a draft under the displayed generation guard. Neither executes anything.

Inspect the saved definition and its hash, then explicitly check the authorization box and Accept reviewed case. Changing the editor clears authorization. Unsaved changes must be saved or reloaded before acceptance or execution; the runtime rejects stale versions independently of the UI. Acceptance is separate from Run accepted case. An accepted case run uses the shared retained-run-UUID path, status controls, cancellation and Human Approval controls. A passing `waiting` expectation is a matched checkpoint, not a completed workflow or permission to approve it.

**Archive reviewed case** and **Restore reviewed case** use the same explicit review authorization, exact saved definition/hash and current generation. Save or reload unsaved editor changes first. Each appends a lifecycle version; the definition and draft/accepted status remain unchanged. Archived cases stay visible but cannot be edited, accepted or newly run. Restore enables a draft's review or an accepted case's explicit run using its new generation; it never executes by itself. Neither action cancels admitted work, decides approvals, deletes evidence or refreshes project pins. After a lost reply, refresh the retained case ID and inspect its generation before another mutation; the viewer never retries or invents newer guards automatically. The scoped `tests.archive` operation accepts only the case ID, expected generation, reviewed hash and boolean archival state; project and actor remain fixed by the owner. Actual browser interaction remains unqualified.

Generate candidate drafts retains a batch UUID and its selected optional API mode before submission. A lost response leaves it pending: another explicit click retries that same batch and mode even after selection changes, while Refresh only retrieves it. Historical retained batches without a mode still use omission. After a successful receipt, another Generate click requests a new batch with the then-selected entry. Generated completion expectations are suggestions requiring review, not correct-output or coverage evidence. A default-mode draft on an API-only graph is not executable until explicitly edited/reviewed/accepted with API mode; no automatic migration occurs. No generation, acceptance, execution or approval occurs on refresh.

Case IDs, batch IDs, the optional batch API mode and pending-batch state may be kept in tab storage; definitions, inputs and expected/actual values are not. Draft/edit/accept mutations are not universally idempotent: after a lost response, inspect the retained case and current generation before another mutation. Refresh or use the owner's CLI/API rather than assuming rollback. Full definitions, generation receipts and test reports are private. Inspect selected run's expected/actual results reads the original accepted case even after later edits; an ordinary non-test run has no test result. Results do not automatically regrade in the panel after an approval—inspect again for the current retained checkpoint.

Missing, incomplete or timed-out replies now show operation-specific guidance instead of raw fetch/decoder errors. Suggested drafts may already be saved: **Refresh saved tests** reads the retained batch, while an explicit **Suggest test drafts** retries a still-pending request with its original UUID and entry. Successful explicit refresh reports that the batch was found and that another suggestion action now creates a new batch; uncertain reads keep the pending identity and do not claim resolution. A lost run reply points to **Refresh status**, not a replacement run; a lost approval reply requires reading and reviewing the current approval before another decision. These messages do not establish failure, rollback or non-dispatch. Existing request identities, the fifteen-second observation timeout, response-size limit, explicit retry guards and definitive server rejection handling are unchanged. Read-only status polling is not mutation replay. The page does not create a replacement identity on transport loss, but the browser network stack can transparently resend the **same** HTTP request after an early connection close; do not interpret the page's lack of an explicit retry as proof of only one wire request. Inspect the original retained identity and guard before taking another action.

**Clear inspected test result** discards only the displayed report and invalidates pending report replies, including a still-running accepted-case submission. It does not cancel that run, delete evidence or submit another request. Changing the selected run clears its report; switching cases fences an earlier definition read. Returning to the same ID does not revive an older reply. The next explicit inspection reads the retained outcome.

Disconnect, a different authenticated session/project pin and pagehide discard the case editor's private values, saved-definition display, generation receipt, result display and review consent. The replacement editor starts with `input: null`, not reconstructed previous input; explicitly load the saved case or edit the new draft before use. Retained case/batch/run IDs and runtime records are not erased by this display cleanup. Late reads or mutation acknowledgements from an old session are ignored without automatic retry; inspect the original identity through its owner after uncertainty. Controls tolerate absent session state and remain unavailable while disconnected or after pagehide. A host refresh arriving after pagehide is refused without a request; pageshow re-enables explicit controls but never reloads private data or executes automatically. Serialized controller tests cover these fences, not actual browser/CSP/layout/accessibility.

Tests and batches remain after server shutdown and prevent deletion of their referenced project. The owner CLI/API can explicitly [export test definitions](transfer.md) as part of a v2 project bundle; batches and results are excluded. Default preview restart creates a separate project; use the explicit reviewed attachment path to reopen the same current generation/revision, or the owner CLI/API for other historical scopes. The viewer has no erasure action. Owner-only [limited unused-draft logical removal](testing.md#sqlite-sdk-logical-removal) is separate from archival; broader case/batch retention, browser suites and physical erasure remain unfinished.

## SDK and remaining scope

For trace-backend navigation, the separate **Load / refresh trace references** panel reads metadata only on explicit request. Add `--trace-viewer-file viewer.json` at local/Docker preview startup to configure a pinned trace-ID route; otherwise the panel shows retained IDs without links. It never probes or opens the backend automatically. See [trace navigation](trace-navigation.md) for configuration, sharing boundaries and the still-open browser/backend qualification gates.

`startRuntimeService({runtime: {dataDirectory}, token, actor, preview: {source}})` opts into the fixed shell and scoped endpoints; imports never start a listener. Normal `runtime serve` remains JSON-only. `POST /v1/preview/bootstrap` takes owner authentication and `{}`; `/v1/preview/operations` and `/v1/preview/logout` accept only scoped credentials. Operations are `view`, `runs`, `run`, `advance`, `show`, `inspect`, `node.inspect`, `evidence`, `cancel`, `approval`, `decide`, and `tests.list|show|history|create|edit|accept|archive|generate|generation|run|result`, strictly restricted to the admitted project/revision. See `src/preview/session.ts` in the development repository for the request schema. One reserved shared request slot remains available for single-run status, guarded Pause and cancellation when ordinary capacity is full.

The `evidence` protocol operation returns a [run snapshot](evidence.md) with payloads/actors excluded by default; optional `includePrivate: true` requires explicit private-data authority. Foreign-project/revision runs are rejected in either mode. The experimental **Prepare snapshot → Download snapshot** controls verify the selected identity, privacy declaration and checksum before exposing an in-memory download link. Private opt-in applies to one preparation only. See [download behavior and browser file-permission limits](evidence.md#html-preview-downloads); actual browser saving remains unqualified.

The protocol also accepts `run` with `paused: true`, guarded `advance` (retained request UUID, checkpoint hash, Step/Continue mode with optional `breakpoints` node-ID array, or cooperative Pause / saved-response recovery without breakpoint changes), and `decide` with `pauseAfter: true`; see [execution controls](control.md). The experimental stepping, breakpoint, Pause and recovery controls call real operations scoped to the admitted project/revision, never on refresh. Browser qualification remains open.

`startPreviewGateway({source, projectId, token, port}, owner)` is the corresponding storage-free SDK host. Supply a trusted authenticated, instance-pinned `owner.call(command, traceParent?)` adapter; this function performs no owner discovery or attestation itself. Closing the gateway does not close that adapter or its runtime. The CLI supplies the verified Docker adapter. Local preview calls the same backend-neutral preview session through direct core operations, not a loopback hop.

This is not yet the full live-preview milestone. Browser verification (including schema-input editing, overlays and saved-case controls), remaining debugging controls, broader Docker profiles and Kubernetes remain open. Bounded schema fields are implemented; controller doubles and generated HTML/hash checks do not prove browser execution, focus handling or visual quality. See [HTTP boundaries](http.md), [saved tests](testing.md) and [cancellation](cancellation.md).
